# 点加算・矩形和：座標型と初期点 build（2026-10-06）

`src/OfflineQuery/point_add_rectangle_sum.rs` をジェネリクス化し、初期点専用の `build` を追加した。public BIT の API、点加算・矩形和の引数順、質問順の返却、solve 後の消去を維持している。

## API

```rust
// points: Vec<(i64, i64, i64)>。最後の要素は重み。
let mut solver = PointAddRectangleSum::<i64>::build(points);
solver.push_add(x, y, w);
solver.push_query(lx, ly, rx, ry); // [lx, rx) × [ly, ry)
let answers = solver.solve();
```

- 型は `PointAddRectangleSum<X = i32, Y = X>` と `PointAddRectangleSumQuery<X = i32, Y = X>`。`::<i64>` は両軸 i64、`::<i128, u64>` は軸ごとに別の型。既存の i32 使用例は型推論・既定型で使える。
- x は `Ord`、y は `Ord + Clone`。x は Clone / Copy を要求しない。整数に限らず文字列や独自の順序型も利用できる。座標の算術・整数へのキャストは行わない。
- 重みと回答は従来どおり i64。演算結果と中間値が i64 に収まる前提も従来どおり。
- `build(points)` は関連関数で、Vec・配列・所有権を渡す iterator を受け取る。初期点を所有し、x 順にソートする。点の重複・負の重みを許す。借用配列からなら `points.iter().copied()`（Copy 座標）や `.cloned()` を渡す。
- 初期点は全操作より前に存在する。以後の `push_add` は登録順の更新であり、後に登録された更新はそれより前の質問に影響しない。
- `solve()` は初期点も更新も質問も消去する。次の solve に初期点を持ち越さない。Clone したソルバーは独立して処理できる。
- 質問は `lx <= rx, ly <= ry` が必要で、逆順を assert で拒否する。空矩形の答えは 0。

## 初期点が速くなる理由

初期点を先頭の加算として扱うと、時間分割の区切りによって、初期点の寄与を複数のノードでソート・走査・逆加算する。新しい build では、初期点から全質問への寄与を一度の x 走査で計算し、後続操作だけを時間分割する。

初期点の x ソートは build 時に一度。solve では質問境界だけを x 順にソートして初期点を挿入し、BIT の y 区間和で寄与を求める。初期点の寄与計算後は BIT を一括ゼロクリアするので、初期点ごとの逆加算も不要。その後に、初期点を含まない動的操作の分割統治を行う。

y の圧縮対象は初期点・更新点だけとし、質問の境界は lower_bound で順位を求める。同一 x の質問イベントは加算より先に処理する。従来の未定義定数 I への依存を除去した。内部の加算イベントの区別には、座標値と衝突しない圧縮添字の番兵を使う。圧縮添字は usize であり、u32 / i32 への変換は不要。

初期 N 点、後続 M 操作として、比較・Clone を定数時間とすれば build を含め概ね `O((N+M) log(N+M+1) + M log(M+1) log(N+M+1))` 時間、`O(N+M)` 空間。初期点がない場合は従来と同じ O(M log²(M+1))。

old は変更前の実装で初期点を先頭 push_add する方式。prepend は新しいジェネリクス版で同じ登録を行う方式。compressed は前回検討の y 圧縮＋第二キー変更のみで、ジェネリクス化していない候補。build は今回の初期点専用処理。

## 検証

- 8種類の分布×3000 seed＝24,000操作列で、初期点からの愚直処理と旧版・圧縮候補・新版の先頭加算・build の4方式を比較。debug / 最適化ビルドとも一致した。
- 6テストで、i32/i64/u64/i128 の端点、x・y が異なる型、Copy ではない y、Clone も要求しない独自 x 型、重複点、負の重み、半開境界、空矩形、質問だけ・更新だけ、空の build、clone、消去と再利用、逆順矩形の拒否を確認した。
- 11大規模ケース×4方式×3回＝132実行で、全回答のチェックサムと回答数が一致した。
- イベントを24バイトに縮めて質問の区間を元データから読む案も試したが、参照先を読む負担で遅くなったため採用していない。最終版は区間順位をイベント内に持つ。
- 外部ジャッジ提出・Linux/x86 の計測は未実施。
