# 整数ソートの実験・検証記録

2026-10-21。 [実装](../src/Basic/integer_sort.rs) · [使い方・アルゴリズム](../../algorithm_set/Basic/integer_sort.md) · [入力付き実行例](../examples/integer_sort.rs)

## 採用した実装

`integer_sort(&mut [T])` と `integer_sort_with_buffer(&mut [T], &mut Vec<T>)`。
対応型は `u32 / u64 / usize / i64`。昇順の整数値ソートで、実装はsafe Rustのみ。
CPU専用命令や外部クレートは不要で、本体1ファイルをコピーして使える。

- 小配列は標準の `sort_unstable`。昇順・非増加の入力は走査または反転で完了。
- 共通の下位bitを除いた値域が十分狭いときは数え上げ。
- それ以外は8/11 bitのLSD基数ソート。変化幅9/10/11 bitでは1パスで分配。
- 最小値との差で桁数が減る場合はキーを正規化し、各パス前に整列が完了していれば打ち切る。
- 変化しない桁を省略し、作業バッファを交互に使う。結果がバッファに残る場合のコピーも計測に含めた。

## 試した候補

[比較実装](support/integer_sort_candidates.rs)と[ベンチマーク](benchmark_integer_sort.rs)を残した。
本体から比較実装を読み込むことはない。

| 候補 | 今回の判断 |
| --- | --- |
| 桁ごとに集計する8/11 bit LSD | 基本方式として採用。小さい桁数には8 bit、大きい入力・広いキーには11 bitが有効 |
| 10/12 bit LSD | 適応型の8/10/11/12 bit比較で、標準設定には11 bitを選択 |
| 16 bit LSD | 一部の狭い分布に強いが、カウンタ初期化と広い書き込み先が負担。全幅乱数では11 bitに及ばず不採用 |
| 全桁のヒストグラムを最初に集計 | 今回は桁ごとの集計より遅く不採用 |
| 境界チェックを省くscatter | 安定した優位がなく、本体はsafe Rustを採用 |
| 8 bit MSD / American flag sort | 追加の入力長バッファを避けられるが、今回の計測では遅く不採用 |
| バケット単位の8/32要素バッファ付きscatter | 8/11 bitの4候補とも全幅乱数で採用方式に及ばず不採用 |
| 狭い値域の数え上げ | 採用。範囲幅が要素数程度まで広いと遅かったので、要素数の1/8以下・最大65,536カウンタに制限 |
| 最小値による正規化・途中の整列完了判定 | 採用。桁の境目や `i64::MIN/MAX` 付近の2群が混在するケースの回帰を解消 |

候補の初回比較は6サイズ・12分布・2型・3回の中央値。
最終比較では13分布と全4型に広げた。候補JSONと最終JSONは別実行なので、
候補の絶対時間を最終版の時間と直接比較しない。

生データ:

- [基本候補1,152測定](integer_sort_benchmark_candidates.json)
- [数え上げ・桁幅などの適応候補864測定](integer_sort_benchmark_adaptive.json)
- [バケットバッファ候補36測定](integer_sort_benchmark_blocked.json)

## 最終実装の実測

ARM64 macOS 26.5.2、rustc 1.93.0、Cargoのrelease既定設定。
`target-cpu=native` やCPU固有機能の指定は使用していない。
入力生成・入力の復元・正解照合・入出力を除き、ソート呼び出し全体を計測した。
`integer_sort` の時間には解析・確保・初期化・最後のコピーを含む。
再利用版は同じ入力サイズの無計時ウォームアップ後のバッファを使用。
1回ウォームアップし、5回の中央値を記録。小さい入力は各回を複数回にまとめて平均する。
メソッドは固定順序で計測しており、特に微小時間の差は実行時の負荷やクロックにも影響される。

100万要素、単位ms。高速化率は `標準 / integer_sort`。

| 入力 | 型 | 標準 | integer_sort | バッファ再利用 | 高速化率 |
| --- | --- | ---: | ---: | ---: | ---: |
| 全幅乱数 | u64 | 11.208 | 7.455 | 7.520 | 1.50倍 |
| 全幅乱数 | u32 | 10.719 | 3.722 | 3.691 | 2.88倍 |
| 全幅乱数 | usize | 11.297 | 7.769 | 7.524 | 1.45倍 |
| 全幅乱数 | i64 | 11.247 | 8.112 | 8.043 | 1.39倍 |
| 16 bit値域 | u64 | 10.123 | 1.657 | 1.692 | 6.11倍 |
| 16 bit値域 | u32 | 9.490 | 1.731 | 1.707 | 5.48倍 |
| 16種類の重複 | u64 | 2.409 | 0.839 | 0.823 | 2.87倍 |
| 上位16 bitのみ変化 | u64 | 10.058 | 1.654 | 1.658 | 6.08倍 |
| MIN/MAX付近の2群 | i64 | 10.083 | 2.937 | 2.919 | 3.43倍 |
| 昇順 | u64 | 0.329 | 0.141 | 0.140 | 2.34倍 |
| 逆順 | u64 | 0.434 | 0.437 | 0.471 | 0.99倍 |
| 1%の位置交換 | u64 | 11.238 | 8.736 | 8.585 | 1.29倍 |

最終比較は16・64・128・256・512・1,024・2,048・4,096・16,384・65,536・20万・100万・400万要素。
全幅乱数、下位32 bit、下位16 bit、16種類、上位16 bit、最大値付近、符号境界付近、
昇順、逆順、1%交換、全要素同一、山型、257周期を対象とした。
全676ケースで標準・新実装・再利用版を照合し、2,028測定を記録した。
`signed_boundary` は生のbit列が `2^63 ± 32768` の入力で、`i64` では `MIN/MAX` 付近になる。
`u32` では上位bitが切り捨てられるため、符号境界の意味は持たない。

小配列には解析のコストがあり、すべての入力での高速化を保証するものではない。
他CPU・他コンパイラ・32 bit実行環境・ジャッジでの速度は未検証。

## 正しさの検証

[テスト](integer_sort.rs)の10本をdebug/releaseで実行。

- 全4型について、4種類の境界値から作る長さ0〜7の全列を標準ソートと照合。
- 128・1,024・2,048・8,192などの切り替え境界を含むサイズ、1〜64 bitの幅、共通の下位bitと固定bitを照合。
- 変化しない中間桁、パス数の偶奇、最上位bitのみの変化、全要素同一を検証。
- 255・1,023・`u32::MAX`・`2^63`・`u64::MAX`付近をまたぐ狭い値域を検証。
- 数え上げの65,536カウンタ上限を使う大配列、最小値による正規化、途中でソートが完了する入力を検証。
- 昇順・非増加・山型・周期列・一部だけ交換した列を照合。
- バッファの縮小・拡張と容量再利用、部分スライスの外側を保持することを検証。

本体に `unsafe` はない。実験用候補の `unchecked8` だけは境界チェックを省くscatterを使う。
外部ジャッジへの提出は行っていない。

入力付き実行例の最大値・重複・空入力、使い方ページのコード例もコンパイル・実行した。
既存解説の実行例11本も通過。解説集全体の `check_docs.py` は、既存の
`algorithm_set/Basic/chminmax.md` が存在せず停止するため、全体成功とはしていない。
今回追加したページの必須見出し・ローカルリンク・一覧掲載は個別に確認した。

## 再現手順

`arcaki_library` で実行する。

```sh
cargo test --offline --test integer_sort
cargo test --offline --release --test integer_sort
python3 tests/run_integer_sort_benchmark.py --full --all-types
python3 tests/run_integer_sort_benchmark.py --mode candidates
python3 tests/run_integer_sort_benchmark.py --mode adaptive
python3 tests/run_integer_sort_benchmark.py --mode blocked
```

各ベンチマークは対応する `integer_sort_benchmark_*.json` を更新する。
`--full` を省くと6サイズ・3回、`--all-types` を省くと `u64/u32` のみで測る。
基本・適応候補の初回JSONは符号境界入力を追加する前の12分布で、再実行時は13分布になる。
比較する際は負荷の大きい他のテスト・処理を同時に実行しない。

入力例の形式は `n` と続く `n` 個の `u64`。

```sh
printf '5\n18446744073709551615 0 9 2 9\n' | cargo run --offline --release --example integer_sort
```

出力は `0 2 9 9 18446744073709551615`。
