# セグメント木・遅延セグメント木の高速化

2026-10-21〜22。通常版、モノイド保持版、遅延版の公開 API・trait の制約を維持。採用した実装には unsafe を追加していない。

## 採用した変更

- 通常版・保持版の `from` は、葉の移動前に同じ場所を単位元で埋めない。通常版では入力の葉の clone も省く。
- 3 実装の境界探索では、判定に使った区間積を次の累積値として再利用する。遅延版は述語が所有値を受け取る既存 API を維持するため clone を使う。
- 遅延作用は内部節点分だけ保持する。未伝播かどうかを別の `Vec<bool>` に記録し、更新のない節点では push を省く。
- 作用の合成は従来どおり行う。「未伝播なら合成、そうでなければ代入」という追加分岐は、区間更新で遅かったため入れない。
- 作用を参照で渡し、push 時は作用を取り出して両方の子に適用する。作用自体の余分な clone を省く。
- 内部長全体への積・更新は根だけを扱う。入力長が 2 の累乗でない場合の論理配列全体はこの近道の対象外。
- `get_slice(l,r)` は対象区間の祖先・内部節点だけを上から展開する。計算量を O(n) から O(log n + r-l) に変更。
- 遅延版 `min_left` の根を越える探索を修正。単一要素 `[7]` で `min_left(1, |x| x.0 <= 6)` が 0 を返していたケースは 1 を返す。
- `bit_length` は `usize::BITS` を使う。32-bit 向けの式も正すが、実行検証は ARM64 のみ。

通常版の論理長、保持版・遅延版の 2 冪に切り上げた内部長とパディングの扱いも維持した。

## 最終測定

Apple ARM64/macOS、Rust 1.89.0、`--edition=2021 -O`。サイズは 1,024 / 100,003 / 1,048,576。乱数・短区間・整列区間・全区間・連続位置を使い、和・行列積・Box の値、加算作用・mod 998244353 のアフィン作用を比較した。

ウォームアップ 1 回、測定 9 回、各回の版の実行順を固定 seed でシャッフル。最終比較は 330 条件、5,940 測定。候補比較も含めると旧版・採用版を含む 30 通り、47,811 測定。入力生成・分岐処理を含む操作列の所要時間で、入出力は含まない。構築と部分取得では、API に伴う確保・破棄を含む。それ以外では構築・破棄を除外する。

速度比は旧版の中央値 / 採用版の中央値。探索の不具合で性能差が出ないよう、参照版にも `min_left` の根のガードだけを適用する。変更前の原本は `support/segment_tree/*_baseline.rs` に保存した。

| 条件 | サイズごとの速度比の範囲 |
| --- | ---: |
| 通常版・行列積のランダム境界探索 | 1.25〜1.28 倍 |
| 通常版・Box 値の構築 | 1.42〜1.64 倍 |
| 遅延版・加算/和のランダム区間取得 | 1.38〜1.55 倍 |
| 遅延版・加算/和のランダム境界探索 | 1.51〜1.66 倍 |
| 遅延版・アフィン/和のランダム区間取得 | 1.70〜2.65 倍 |
| 遅延版・アフィン/和のランダム境界探索 | 1.69〜2.51 倍 |
| 遅延版・アフィン/和のランダム一点取得（未更新） | 4.36〜7.93 倍 |
| 遅延版・アフィン/和のランダム更新と取得の混在 | 1.09〜1.19 倍 |
| 遅延版・加算/和のランダム区間更新のみ | 0.91〜0.92 倍 |
| 遅延版・短い部分取得（毎回全体に加算） | 加算 10.97〜3,354.88 倍、アフィン 13.80〜4,563.99 倍 |

普通の整数和を使う通常版の基本操作はおおむね同等。重い演算や clone を伴う構築・探索で差が出る。遅延版も全条件で速くなるわけではなく、軽い加算のランダム更新のみでは約 9% 遅く、加算のランダム更新と取得の混在では約 4〜5% 遅かった。境界探索の前に更新する条件も測定し、最大約 16% の所要時間増加を観測した。大きな部分取得の改善率は、木全体を展開していた旧版との計算量の差による。

`S=(u64,u64), F=(u64,u64)`、内部長 2^20 の配列領域は、従来の約 64 MiB から約 49 MiB に減る。`Vec` ヘッダ・allocator の管理領域を除く計算値。作用がゼロサイズの型では pending 配列分の領域が増える。

[最終生データ](segment_tree_benchmark_results.json)と[集計](segment_tree_benchmark_summary.json)に各条件・各回の時間を残した。集計には独立 resampling 2,000 回による中央値比の percentile 95% 区間も含む。条件ごとの探索的な区間で、多重比較補正はしていない。バックグラウンド負荷、キャッシュ、コード配置などの影響を受けるため、僅差は安定した改善と扱わない。ローカルの測定であり、外部ジャッジでの速度は未確認。

## 比較して採用しなかった案

- `#[inline]` の全指定、`#[inline(always)]` の全指定。
- 探索の繰り返しシフトを `trailing_zeros` に置き換える案。
- 読み取りを `get_unchecked` に変える案。
- 一回の slice 取得で兄弟の境界チェックをまとめる案。
- 未伝播なら作用を合成し、そうでなければ代入するフラグ方式。
- `Option<F>` に未伝播状態を格納する案。
- 境界の共通祖先の push/update を重複排除する案。
- 両端の push を別ループにし、末尾のゼロ数から開始する案。
- 通常版の空・一点・全区間取得の個別分岐。

たとえば最初のフラグ方式は取得中心では速い一方、ランダムな加算更新で旧版の約 1.8 倍の時間を要した。境界の重複排除も、安い演算の更新が多い条件では分岐のコストが勝った。採用版はこれらの悪化を小さくした組み合わせ。

## 正しさと再現手順

`segment_tree_optimization.rs` で空・単一要素・2 冪境界、42,000 回のランダム操作列と素朴配列との比較、非可換な文字列結合、非 Copy な作用の合成順、両方向の境界探索、部分取得、保持モノイドの実行時パラメータ、パディング互換性を確認する。単なる旧版比較だけでなく期待値を独立に求める。`structures.rs` の既存テストも使用する。

Rust 1.93.0 の全体 debug テストは 218 件通過（7 件 ignored）。Rust 1.89.0 と 1.93.0 の debug/release で、対象 6 件と既存構造テスト 5 件の計 11 件ずつが通過。警告なし。公開ソースが最終測定時の SHA-256 と一致することも確認した。

以下は `arcaki_library` ディレクトリで実行する。

```sh
cargo +1.89.0 test --offline --test segment_tree_optimization --test structures
cargo +1.89.0 test --offline --release --test segment_tree_optimization --test structures
python3 tests/run_segment_tree_benchmark.py --validate --variants baseline,current --sizes 1024,100003,1048576 --repeats 9
python3 tests/summarize_segment_tree_benchmark.py
```

候補をすべて再測定する場合は `--variants` を省略する。生成処理は `support/segment_tree/candidates.py`、操作列は `support/segment_tree/benchmark.rs`。候補の `--validate` でも同じ独立モデルテストを実行してから測定する。全比較で操作列と最終 checksum が一致することを確認する。

探索的な各段階の結果は `segment_tree_candidates*.json` に保持した。初期段階から順に、行列積・Box 型・最終サイズの条件を増やしているため、各段階の測定条件はそのファイルの行を参照する。最終測定にはソースと測定用ファイルの SHA-256 を記録した。
