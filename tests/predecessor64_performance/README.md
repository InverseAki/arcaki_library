# Predecessor64 高速化の検討（2026-10-07）

## 結論

推奨は **更新時の逐次シフト + 等号込み検索の統合 + 階層の連続配列化**。
`flat.rs` の `Flat` が、この組み合わせを試した安全な Rust の実装。
調査時点では本体を変更せず比較した。その後、ユーザーの指示により
`src/DataStructure/predecessor64.rs` にこの組み合わせと端のワードを先に見る min/max を反映した。
以下の候補比較で「現実装」と記したものは、調査開始時の旧実装 `baseline.rs` を指す。

## 本体への反映と再確認

公開メソッド名・引数型・返り値・見つからない場合の `!0` を維持した。
全コンストラクタを移植し、空の入力は値域1、文字列は64の倍数へ切り上げる挙動も維持。
`new` は正の値域で使い、操作位置は値域内とする。

本体を旧実装と再比較した結果（44条件、100万操作×7回、Rust 1.89.0 `-O`）:

| 操作 | 本体の処理時間短縮率 |
|---|---:|
| 狭義検索 | 13.2% |
| 等号込み検索 | 28.2% |
| 更新 | 24.3% |
| 混合 | 15.8% |

数値は条件別の測定中央値の比を幾何平均したもの。
候補の測定との差には別実行での測定変動を含む。
`results_1.89.0_default_current.csv` と `summary_1.89.0_default_current.json` に保存。

コンストラクタでは、受け取った Vec の後ろに上層を追加し、
`reserve_exact` で必要量を確保する。各64ワードをまとめて1個の要約ワードへ変換する。
`from_vec_usize` は消費する Vec の `into_iter` を使い、不要な複製を減らす。

構築の別測定（21回の中央値、入力の用意と集合の破棄は時間から除外）:

| 入力ワード数 | 内容 | コンストラクタ | 旧実装 | 本体 |
|---|---|---|---:|---:|
| 4,097 | 全ワード非零 | from_vec_u64 | 8.67µs | 1.17µs |
| 262,145 | 全ワード非零 | from_vec_u64 | 517.75µs | 66.42µs |
| 262,145 | 全ワード零 | from_vec_u64 | 97.79µs | 66.33µs |
| 262,145 | 64ワードごとに1個非零 | from_vec_usize | 151.54µs | 66.25µs |
| 4,097 | 全ビット1 | from_01_string | 552.83µs | 548.54µs |

文字列からの構築はバイトの解析が主体で、ほぼ同速だった。
生データは `constructors_1.89.0_default_current.csv`。

`tests/predecessor64.rs` の全10テストがRust 1.89.0のdebug/releaseで通過。
既存のモデル・境界テストに、本体そのものと全コンストラクタのテストを追加した。
空・密・疎のビット列、階層境界、余分な capacity、文字列のパディング領域への更新、
バイト単位の入力解釈、clone後の更新の独立性を確認した。

## 調査時点の候補比較

Rust 1.89.0、aarch64-apple-darwin、`-O`、通常の CPU 設定で、
各条件の測定中央値を現実装で割り、その比の幾何平均を取ると次の結果になった。
数値は**処理時間の短縮率**であり、スループットの増加率ではない。

| 候補 | 狭義検索 | 等号込み検索 | 更新 | 混合 |
|---|---:|---:|---:|---:|
| 更新だけ変更 | 0.4% | 0.1% | 19.0% | 6.8% |
| 更新変更 + 検索統合（Incremental） | 2.8% | 28.3% | 17.4% | 13.5% |
| 上記 + 最下層の検索を分離（LeafFirst） | 9.9% | 28.8% | 18.2% | 13.4% |
| 更新変更 + 検索統合 + 連続配列（Flat） | **13.2%** | **30.6%** | **25.5%** | **18.1%** |
| 連続配列 + ワードのシフト検索（FlatShifted） | 13.9% | 32.8% | 25.9% | 18.0% |

`Flat` は主要な44条件すべてで現実装より短い測定中央値となった。
条件別の時間比は、狭義検索 0.778–0.907、等号込み 0.454–0.884、
更新 0.581–0.901、混合 0.727–0.881。
これはこのローカル測定の結果であり、常に同じ差が出る保証ではない。

`-C target-cpu=native` でも `Flat` は、狭義検索13.9%、等号込み31.4%、
更新27.1%、混合18.1%の時間短縮となった。

## 具体例

以下は通常の CPU 設定での1操作あたりの時間（ns、7回の中央値）。
初期集合は stride ごとに1点をランダムに配置する。
更新・混合ではこの点の集合内で挿入と削除を行うので、測定中の密度は変わる。

| 値域 | 初期 stride | 操作 | 現実装 | Flat | FlatShifted |
|---|---:|---|---:|---:|---:|
| 262,144 | 2 | 等号込み検索 | 8.38 | 4.18 | 3.71 |
| 262,144 | 2 | 更新 | 6.26 | 3.72 | 3.68 |
| 262,144 | 2 | 混合 | 8.75 | 6.37 | 6.30 |
| 262,144 | 4,096 | 狭義検索 | 9.65 | 8.47 | 8.72 |
| 262,144 | 4,096 | 混合 | 10.73 | 9.33 | 9.42 |
| 16,777,216 | 64 | 混合 | 11.34 | 9.99 | 10.58 |

ワードをシフトする案は密な集合の等号込み検索に特に効くが、
疎な集合ではマスク方式に負ける場合がある。
全体の混合性能には差が小さいので、まず `Flat` のマスク方式を推奨する。

## 変更の理由と不変条件

### 1. 更新時のシフトと上層への伝播を減らす

現実装は各階層で `p >> (6 * i)` を計算する。
候補では現在の位置だけを保持し、次の階層へ進むときに `p >>= 6` を行う。
更新対象も `&mut word` を一度取って処理する。

挿入は `old = *word; *word |= mask; if old != 0 { return; }` とする。
挿入前からワードが非空なら、上層の対応ビットは既に1なので上層に進む必要がない。
現実装では、同じワードに新しいビットを追加すると上層を一度確認してから止まる。
この確認を省略する効果が、密な集合の更新で大きい。

削除は `*word &= !mask` とし、ワードが非空のままなら終了する。
空ワードへの削除も終了させるので、存在しない要素の削除で上層を壊さない。
全体が空になる場合は根までクリアする。

重複挿入と不在要素の削除だけを繰り返す別測定でも `Flat` は高速だった。
初期 stride 2/64/4096 の6条件で、現実装1.19–1.52nsに対し0.73–0.98ns。
ただし更新だけの変更では、不在・重複操作はほぼ同速となる条件もある。

### 2. 等号込み検索を1回で行う

現実装の `inprev` / `innext` は `include` を先に行い、存在しないときに再検索する。
最下層のマスクを等号込みにして検索を直接行う。
上層では「現在の子ワードの隣」を探す必要があるので、引き続き狭義のマスクを使う。

- `inprev` の最下層: `u64::MAX >> (63 - (p & 63))`
- `innext` の最下層: `u64::MAX << (p & 63)`
- 狭義 `next` のマスク: `(u64::MAX << (p & 63)) << 1`

最後の式はシフトを2回に分けることで、64ビットシフトを避ける。
狭義と等号込みは const generic の補助関数にまとめ、公開メソッドの名前と返り値は維持できる。

### 3. 階層を連続した配列に置く

`Vec<Vec<u64>>` を `Vec<u64>` と階層の開始位置に置き換える。
階層ごとの Vec のポインタを取り出す処理を減らし、割当もまとめられる。
候補では最大11階層を固定長の offset 配列に記録した。
64ビット usize のビットを6ビットずつ要約するので、この数で足りる。
データの添字アクセスには通常の境界検査を残している。`unsafe` は使用していない。

これはアルゴリズムや64分木の次数を変えずに取り入れられる。
今回の比較では、ワードをシフトする追加案より効果が安定していた。

### 4. min/max は端のワードを先に見る

根から直接下りるだけの案は、空集合や中央の1点だけの集合で速くなったが、
密な集合では6ビット階層を全部下りるため遅くなった。
値域262,145・密な集合で、現実装3.58nsに対し根から下りるだけでは5.17nsだった。

最終候補は、最初/最後の最下層ワードに要素があれば即座に返し、
なければ根を見て下りる方式にした。

| 集合 | 現実装 | 最終 Flat | 時間短縮 |
|---|---:|---:|---:|
| 空 | 6.88ns | 3.86ns | 約44% |
| 中央の1点 | 7.32ns | 5.43ns | 約26% |
| 各ワードの末尾 | 6.24ns | 4.49ns | 約28% |
| 偶数すべて | 3.62ns | 3.52ns | 約3% |

密な集合の差は小さい。主な効果は、端に要素がない集合での上昇処理の省略。
主要44条件のベンチマークには `min` / `max` を含めず、この表を別に測定した。

## 検証と測定条件

- 実機: aarch64-apple-darwin。x86_64や外部ジャッジでの性能は未検証。
- Rust 1.89.0で全7実装のdebug/releaseテストが通過。
  初期の検索・更新候補はRust 1.93.0でもテストした。
- 値域64 / 4,096 / 262,144 / 16,777,216、初期stride 2 / 64 / 4,096。
  strideが値域を超える条件を除いた11条件を使った。
- 各条件につき狭義検索・等号込み検索・更新・50%更新の混合を測定。
  合計44条件、各100万操作、7回測定、実装の実行順を巡回。
- 更新は固定した初期点のプール内で行い、約25%は集合を変えない操作。
  各測定の開始時に集合を作り直し、生成・構築・入出力は時間から除外。
- 同じ入力列を全実装に与え、検索結果のチェックサムを照合。
  更新の正しさは別のモデルテストで検証。最適化による計算削除を防ぐため `black_box` を使用。
- 小さい値域1–10の全部分集合・全検索位置を網羅。
  挿入・削除の繰り返し、空集合、全要素の挿入と順/逆順削除も確認。
- 64 / 4,096 / 262,144の前後と非64倍数の値域、16,777,217までを確認。
  各値域2万ステップの更新・検索を `BTreeSet` と照合。
- 空集合、中央の1点、ワード末尾、密な集合、不在・重複更新の追加測定。

調査用の各試作は `new` と集合操作の比較用。
全コンストラクタの移植・構築性能比較は、本体への反映時に別途行った（上記参照）。
操作位置は `p < mx`、値域は正の範囲を対象とした。
ベンチマークの初期状態が異なれば、ここでの平均や最速の候補も変わる。

## ファイルと再実行

- `baseline.rs`: 調査開始時の本体のコピー。
- `update_only.rs`: 更新だけ変更した候補。`prepare.py` で生成。
- `candidates.rs`: Incremental / LeafFirst / Shifted。
- `flat.rs`: Flat / FlatShifted。`prepare.py` で生成。
- `model.rs`: 全実装のモデル・境界テスト。
- `bench.rs`: 主要44条件のベンチマーク。
- `edges.rs`: 空集合・1点・ワード末尾・密な集合の追加測定。
- `noops.rs`: 変化しない挿入と削除の測定。
- `summary_1.89.0_{default,native}.json`: コンパイラ情報、条件別の中央値・範囲・比率。
- `results_1.89.0_{default,native}.csv`: 主要条件の生データ。
- `edges_1.89.0_default.csv` / `noops_1.89.0_default.csv`: 追加測定の生データ。
- `edges_root_only_1.89.0_default.csv`: 端のワードを先に見る前の比較用データ。

arcaki_library のディレクトリで:

```sh
python3 tests/predecessor64_performance/run.py --toolchain 1.89.0 --edges
python3 tests/predecessor64_performance/run.py --toolchain 1.89.0 --native
```

`--count` と `--repeats` は主要44条件の操作数・測定回数。
`--edges` の追加測定は各100万操作・7回固定。
生成されるCSV/JSONは同名の測定結果を上書きする。

根から下りるだけの旧案を再現するには、`prepare.py --root-only` で候補を生成し、
`edges.rs` を `rustc +1.89.0 --edition=2021 -O` で直接ビルドする。
通常の `prepare.py` または `run.py` を実行すると最終候補に戻る。

主要44条件は端のワードの高速経路を追加する前に測定したが、
そこで測定する検索・更新メソッドの実装は最終候補と同じ。
端のワードの高速経路を追加した後にモデルテストと追加測定を実行した。
