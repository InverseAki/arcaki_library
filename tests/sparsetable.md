# Sparse Table の高速化

2026-10-21。Rust 1.89.0、Apple arm64、`--edition=2021 -O`。
競技ジャッジへの再提出はしていない。

## 採用した構成と API

`SparseTableMI::build(a)`、`SparseTableMX::build(a)`、
`SparseTableMI::build_by_key(a, key)` は `Vec<T>` の所有権を受け取る。
入力のバッファをそのまま保持する。元の配列が必要なら呼び出し側で `clone()` する。
LCA側の呼び出しも更新した。

標準の表の要素分が16 MiB以下なら、二次元配列を使い、区間検査後に
二点を直接参照する。この場合も入力のコピーは行わない。
16 MiBを超える場合は16要素を1ブロックとする。入力値と各ブロック内の prefix / suffix、
ブロック全体の min/max に対する1次元 Sparse Table を保持する。
同一ブロック内は最大16要素の走査、ブロックをまたぐ区間は左右の端と
中央の完全なブロック区間を合成する。

中央の表の段 k の開始位置は `k * (m + 1) - (2^k - 1)`。
段の開始位置配列へのアクセスを省いた。表全体の大きさはchecked加算で求め、
オフセット計算は中間値のオーバーフローにも対応する。
構築はsafe Rustのみ。質問は最初に `l < r && r <= n` を検査し、
構築時に保証した長さに対して `get_unchecked` を用いる。
不正区間はreleaseでもpanicする。

ブロック版は m = ceil(n / 16) として構築・空間 O(n + m log m)、質問 O(1)。
直接参照版は構築・空間 O(n log n)、質問 O(1)。
ブロック幅を固定した実装なので、構築・空間の漸近計算量は O(n log n) のまま。
キー付き最小値は同値なら先頭、最大値は従来どおり同値なら末尾を選ぶ。
`Clone` / `Debug` は維持した。

n = 1,000,000、Tがi32またはu64のとき、保存する T の個数は旧18,951,445個から
3,934,481個へ約79%減る。Vecの余剰容量や管理情報はこの数に含めない。

## 提出コード全体の比較

ユーザーの提出の Input / Output をそのまま使い、Sparse Table と所有権を渡す
呼び出しだけを変更した。各プロセスの入力・構築・質問・出力・破棄を含む経過時間。
入力配列は i32。旧版は直前の `zip / map / collect` の二次元配列実装。

固定シード、実行順を回転、ウォームアップ2回の後の9回の中央値。
全候補の出力全体をSHA-256で旧版と照合した。
生の測定値は [sparsetable_benchmark_results.json](sparsetable_benchmark_results.json)。
構築・質問を分けた17候補の測定値は
[sparsetable_candidate_benchmark_results.json](sparsetable_candidate_benchmark_results.json)。

| 入力・質問 | 旧版 | 採用版 | 旧 / 新 |
| --- | ---: | ---: | ---: |
| n=q=500,000、広い区間 | 28.950 ms | 23.936 ms | 1.21 |
| n=q=1,000,000、広い区間 | 64.556 ms | 46.026 ms | 1.40 |
| n=q=500,000、長さ1〜64 | 30.598 ms | 25.660 ms | 1.19 |
| n=100,000、q=1,000,000、広い区間 | 27.223 ms | 26.928 ms | 1.01 |
| n=q=500,000、同一16要素ブロック内 | 31.256 ms | 28.421 ms | 1.10 |

n=q=1,000,000 の最大RSSは102.23 MiBから42.52 MiBへ減少。
RSSには入力バッファなども含む。時間・RSSともこのローカル環境での値であり、
ユーザーの68msに対する変更後のジャッジ時間は未確認。

## 構築・質問を分けた確認

u64配列の再測定。構築は9回の中央値、質問は200万回を7回測った中央値。
詳しい数値は [sparsetable_phase_benchmark_results.json](sparsetable_phase_benchmark_results.json)。

| 条件 | 旧版 | 採用版 |
| --- | ---: | ---: |
| n=1,024、質問のみ | 3.377 ms | 2.390 ms |
| n=100,000、質問のみ | 3.965 ms | 3.654 ms |
| n=1,000,000、通常の最小値の構築 | 4.494 ms | 1.615 ms |
| n=1,000,000、キー付き最小値の構築 | 16.168 ms | 2.901 ms |
| n=1,000,000、質問のみ | 15.366 ms | 12.618 ms |

直接参照版への切替により、小規模な表の質問速度低下はこの測定では解消した。
ただし17候補の比較では、u32・n=500,000・長さ1〜64の100万質問のみを測ると、
旧版3.710 msに対して採用版4.924 msだった。同条件に近い提出全体では、
構築・メモリ確保を含めると上表のとおり改善している。
質問のみの性能と、入出力・構築を含む性能は区別する。

## 比較した候補

`tests/support/sparsetable_candidates.rs` と
`tests/benchmark_sparsetable_candidates.rs` に実験用コードを残した。

| 番号 | 候補 |
| --- | --- |
| 0 | 提出版の二次元配列、借用入力 |
| 1 | 二次元配列、所有入力 |
| 2 | 二次元配列、所有入力、検査後の直接アクセス |
| 3 | 1次元、開始位置配列、安全なアクセス |
| 4 | 1次元、開始位置配列、検査後の直接アクセス |
| 5 | 1次元、開始位置を式で計算、安全なアクセス |
| 6 | 1次元、開始位置を式で計算、検査後の直接アクセス |
| 7 | 1次元、開始位置配列、初期化済み領域へ構築 |
| 8〜10 | ブロック内単調スタックのビットマスク、幅16/32/64 |
| 11 | 各段をBoxスライスに格納 |
| 12 | 各段を同じ長さにした1次元配列 |
| 13〜15 | prefix / suffix、幅4/8/16 |
| 16 | 本体の採用実装 |

加えて提出コード全体で prefix / suffix の幅32/64も比較した。
1次元化だけの改善は全体時間では安定しなかった。
幅32/64は広い区間ではさらに速い場合があるが、短区間の走査が増えるため、
通常・短区間・キー付き比較のバランスから幅16を採用した。

u64の小規模な表で質問だけを測ると、ブロック版に速度低下があったため、
16 MiB以下の表には直接参照版を使う。両分岐を同じ愚直解と照合し、
100,000 / 200,000要素のu64で自動切替も検証した。
16 MiBは今回の環境と測定規模に基づく固定の切替基準。
ビットマスク方式は構築時の分岐が多く、通常のi32の提出全体では
prefix / suffix より遅かった。

質問だけを繰り返す条件、値の型、キー関数、区間長の分布によって順位は変わる。
自動切替を含めても、すべての環境・質問分布で最速になることは保証しない。

## 再計測

提出と同じ入出力を使う場合:

```sh
python3 tests/run_sparsetable_benchmark.py --submission /path/to/submission.rs
```

`--submission` を省くと現在の `basic_io.rs` / `basic_output.rs` を使う。
提出用の単一ファイルを生成する場合は `--export /tmp/static_rmq.rs` を付ける。

構築・質問を別々に測る場合:

```sh
rustc +1.89.0 --edition=2021 -O --test tests/benchmark_sparsetable.rs -o /tmp/benchmark_sparsetable
/tmp/benchmark_sparsetable --ignored --nocapture
rustc +1.89.0 --edition=2021 -O --test tests/benchmark_sparsetable_candidates.rs -o /tmp/sparsetable_candidates
/tmp/sparsetable_candidates --ignored --nocapture --test-threads=1
```

候補比較は u32 / u64 と、usizeの頂点番号から外部の値を読むキー付き比較を実行する。
`ST_N` / `ST_Q` / `ST_ROUNDS` で規模・測定回数を変更できる。
質問分布は広い区間、長さ1〜64、2冪長。
各候補の構築と質問を分けて記録し、各質問列の答えの合計も旧版と照合する。
入力Vecの用意は構築計測外。借用版で必要になる追加コピーは構築計測に含む。

## 正しさ

`sparsetable_lca.rs` の4テストと `sparsetable_properties.rs` の6テストを
Rust 1.89.0のdebug/releaseで確認。

- 直接参照・ブロック版の両方で全区間・ランダム区間と愚直解の比較。
- 16要素ブロック、2冪、末尾の部分ブロックの境界。
- 単調列、同値、重複、整数の最小・最大値。
- min / max / キー付き比較の同値の選択。
- Ordを持たないpayload、Copyを持たないキー、ゼロサイズの値。
- 入力バッファの再利用、Clone後の独立性、不正区間のpanic、自動切替。
- 各種木のLCA・距離、10万頂点の星型木と保存量。

`examples/static_rmq.rs` は所有権を渡す呼び出し例。
